⏺ M5Unified has full Tab5 battery support via INA226 + I/O expander. Here's the design:

  What M5 gives us for Tab5

  ┌──────────────────────────────┬───────────────────────────────┬───────────────────────┐
  │             API              │        Implementation         │         Notes         │
  ├──────────────────────────────┼───────────────────────────────┼───────────────────────┤
  │ M5.Power.getBatteryLevel()   │ INA226 bus voltage / 2 cells  │ Returns 0-100, or -2  │
  │                              │ → linear 3.3V=0%, 4.15V=100%  │ if unsupported        │
  ├──────────────────────────────┼───────────────────────────────┼───────────────────────┤
  │ M5.Power.isCharging()        │ I/O expander pin (CHG_STAT)   │ enum: charging /      │
  │                              │                               │ discharging / unknown │
  ├──────────────────────────────┼───────────────────────────────┼───────────────────────┤
  │ M5.Power.getBatteryVoltage() │ INA226 bus voltage in mV      │ Pack voltage          │
  ├──────────────────────────────┼───────────────────────────────┼───────────────────────┤
  │ M5.Power.getBatteryCurrent() │ INA226 shunt current in mA    │ Signed: + = charging  │
  └──────────────────────────────┴───────────────────────────────┴───────────────────────┘

  The SoC math is naive (linear voltage curve, no load compensation) but adequate for a
  status indicator.

  Proposed PAL API

  Minimal — just what we need to display:

  // pal.h
  namespace pal {
      int  getBatteryLevel();   // 0-100, or -1 if unknown/unsupported
      bool isCharging();
  }

  Tab5: wraps M5.Power with internal 1-second cache (I2C reads aren't free, no need to hammer
   them at 60fps).
  Desktop: stub — returns -1 and false.

  Display

  The header has room — currently [Span] [Freq] [FPS]. I see two options:

  Option A: Add a separate label on the far right
  Span    CW 14.074.000    46FPS    BAT 85%+

  Option B: Combine into the FPS label (more compact)
  Span    CW 14.074.000    46FPS  85%+

  The trailing + indicates charging; BAT --% (or just hidden) when unknown.

  Update cadence

  Battery state changes slowly. A 1-second internal cache in the PAL is plenty — every call
  returns the cached value cheaply, refresh happens transparently. App tick reads it at 60fps
   for free.

  Things to decide

  1. Display location: separate label (Option A) or merged with FPS (Option B)?
  2. Visual format: text only (BAT 85%+), or a tiny ASCII battery bar (e.g., [████░] 85%), or
   both?
  3. Show on desktop? Hide the label entirely when unsupported, or show BAT --% to keep the
  layout consistent across builds?
  4. Charging indicator: just + suffix, or different color (green when charging)?

  My defaults if you don't specify: Option A, text BAT 85%+ format, hide on desktop, white
  text (no color change for charging — keeps it simple).

⏺ Good catch. Two ways to handle this:

  Option 1: PAL self-caches (no refactor needed)
  PAL stores battery in internal cache, refreshes on next call after 1s expiry. App calls
  pal::getBatteryLevel() every frame — gets cached value cheaply. CAT's existing polling
  stays as-is. Zero changes to cat.cpp. Trade-off: two independent 1Hz timers (CAT's internal
   one + PAL's), and the cadence isn't actually shared.

  Option 2: Lift the 1Hz timer to app.cpp (proper refactor)
  - Remove s_last_poll / POLL_INTERVAL_US gate from inside cat::poll()
  - Split CAT into:
    - cat::poll() — RX accumulation only, called every frame
    - cat::tick1Hz() — the periodic command sends (FA;MD; etc.), called by app
  - Add pal::pollBattery() that the PAL uses to refresh its cached values
  - In app::tick(), add a single 1Hz gate that calls cat::tick1Hz() + pal::pollBattery()

  // app.cpp
  void app::tick() {
      // ... per-frame work ...
      cat::poll();  // RX, every frame

      static int64_t last_slow = 0;
      if (t0 - last_slow >= 1000000) {
          last_slow = t0;
          cat::tick1Hz();         // periodic CAT commands
          pal::pollBattery();     // refresh battery I2C reads
      }
  }

  This gives one shared cadence; PAL battery stays trivially cheap (getBatteryLevel() just
  returns the cached int), and adding future periodic tasks (IMU, temperature, etc.) is a
  one-liner.

  I'd recommend Option 2 — small refactor, cleaner long-term, and matches your intent. Sound
  good?
